# Trunk Base Development

One liner:

***A source-control branching model, where developers collaborate on code in a single branch called ‘trunk’ *, resist any pressure to create other long-lived development branches by employing documented techniques. They therefore avoid merge hell, do not break the build, and live happily ever after.***

Different types of development git workflows:

* GitHub flow
* Gitflow
* Trunk-based development

Addressing issues with low and high volume of commits per day and CI and CD.

## GitHub flow - my thoughts

* Simple and great for Fork vs Shared repo model

  * Open source repo: only Maintainers have write access to upstream and Contributors fork the repo.
  * Shared repo: all Contributors including Maintainers have access.

* Works well when you do not have control over individual Contributors
* Uses GitHub for a distributed approach and is managed using
* Upstream is the choke point for Maintainers to review PRs. In other words, slow release cycles.
* Leverage GitHub PRs for rollbacks.

## Gitflow - my thoughts

* More structured and timed releases. i.e., Every 2 weeks or month or quarter.
* Concept of the dev, qa, release (production) branches
* More maintenance on Maintainers to keep the branches in sync. More opportunity for complex git history and rollbacks are painful.

## Trunk-based development - my thoughts

* Like GitHub flow but more fancy.
* Requires a mature dev team and DevOps team.
* Great for large internal dev orgs for small to large velocity of git commits per day volume.
* With all the quality checks, it could be possible for Continuous Delivery and Deployment with feature flags.
